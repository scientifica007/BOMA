## Plan — الخطة وضوابطها
**الهدف:** جعل GitHub مصدراً موثوقاً لعمل بشري–آلي تفاعلي خاضع لـPDSA، من دون بحث غير مراقب أو دمج تلقائي، مع إبقاء كل البراهين والتجارب المغلقة والمفاهيم المعمارية كما هي.

**الثوابت:** لا تعديل على ملفات Lean المقبولة أو manifests، ولا تغيير `SELECTS` أو `CA-20`، ولا تلاعب بخطط أو نتائج Study/Act مغلقة، ولا بدء 016 أو 017، ولا إلغاء أدلة Meta-PDSA التاريخية. كل خطوة تقنية في فرع صيانة خاص بها، وتبدأ من `current main` جديد.

### حزمة العمل A — حماية main
1. يفحص المالك إعدادات `Settings → Rules → Rulesets` في `scientifica007/BOMA`.
2. إنشاء Branch ruleset يستهدف Default branch / `main`: منع الحذف والـforce-push؛ فرض Pull Request؛ إعداد عدد الموافقات بما يلائم وجود مراجعين مستقلين، دون اشتراط موافقة مستحيلة في مشروع فردي.
3. إعداد بوابة CI دائمة التنفيذ لكل PR قبل فرض status check required. لا تعتمد كشرط إلزامي على workflow قد يُتخطى عبر `paths` لأن هذا قد يترك الفحص `Pending`.
4. تفعيل التحقق المطلوب بعد التأكد من ظهوره واجتيازه على PR تجريبي؛ التحقق من أن كتابة Git المباشرة إلى `main` لا تمر دون السلطة المطلوبة.
**بوابة A:** إعداد Ruleset فعال، مرور تجربة PR عادية، وعدم القدرة على دفع تغييرات مباشرة غير مراجعَة.

### حزمة العمل B — إيقاف المحرك آلياً مع حفظ التاريخ
1. إبقاء الجدولة القديمة معطلة؛ تعطيل Workflow `BOMA Autonomous Research Engine 001` من GitHub Actions، بما في ذلك `workflow_dispatch` المنتج للكتابة.
2. مراجعة أي Tasks/Automations متكررة تخص BOMA وتعطيلها؛ لا ينشأ جدول بديل.
3. بعد التأكد من غياب المستهلكين المصرح بهم، إبطال `AUTONOMY_GH_TOKEN` والاعتماد الخارجي `AI_API_KEY` الخاص بالمحرك أو تقليصهما، دون تسجيل قيمهما أو كشفها.
4. فصل واختبار مسار CI للتحقق فقط؛ لا تُعطل اختبارات البرهان والتدقيق. الحفاظ على `.autonomy` وسجلات G1–G8 كأدلة تاريخية.
5. في PR مستقل، إلغاء صلاحيات التشغيل الذاتي الفعلي في إعدادات التنفيذ، وتحديث الحوكمة والحالة والوثائق المرجعية لتعكس نمط التفاعل.
**بوابة B:** لا scheduled أو manual engine research writes، ولا رمز كتابة غير ضروري، وبقاء CI البحثي متاحاً عند الطلب.

### حزمة العمل C — إحكام بروتوكول الجلسة
1. أمر مالك محدد → قراءة `current main` وحالة البرنامج → Plan نطاق/مخرجات/شروط نجاح.
2. إن كانت المهمة علمية: فرع منفصل وخطة مجمدة مستقلة قبل Do، وعامل علمي واحد؛ إن كانت صيانة: Plan إصلاح محدد مع ضوابط عدم تغيير المعرفة المقبولة.
3. تنفيذ Do بالطلب، تحقق Lean/CI والأدلة الدقيقة، ثم Study وAct وحفظ الفشل والتبعيات.
4. PR لا يدمج ذاتياً؛ يقدم للمالك النتائج والفروق والقرارات. أي انتقال لتجربة أخرى أو تغيير قبول يتطلب أمراً جديداً.
**بوابة C:** تجربة كاملة غير بحثية (صيانة) على هذا الأسلوب مع مراجعة بشرية وتحقق قابل لإعادة الإنتاج.

### حزمة العمل D — قرار استئناف البحث
تظل `ST2-EXP-016` `NOT_STARTED / NO_FROZEN_PLAN` في `OWNER_REQUIRED`. لا تتحول إلى Plan إلا بأمر منفصل من المالك بعد إغلاق حزم الأمن والحوكمة، وبالالتزام بعاملها المعلن دون استعارة نتيجة مسبقة. أما 017 فمشروطة بما تثبته 016 فعلياً.

## Do — ما نفذته مهمة التسجيل هذه
قراءة نسختي التقرير المرفقتين، ومطابقة Git blob لكل منهما مع الملف الموجود، وإعداد قرار التشغيل الجديد وسجل الأدلة وهذه الخطة على فرع توثيق مستقل، دون تعديل `main` أو العمل الرياضي أو المحرك.

## Study — أدلة قبول مهمة التوثيق
يُتحقق بعد إنشاء PR من: صحة HEAD المرجعي، اقتصار الفروق على ملفات التوثيق الجديدة، سلامة الارتباط بالتقريرين وPR #25، غياب أي تعديل على المصدر المقبول، ونجاح فحوص PR المنطبقة. إذا تعذرت CI فلا يُستنتج PASS من السكوت.

## Act — الحكم المسموح به
يعرض PR للمالك للتدقيق. لا يُدمج قبل اختيار حماية `main` المناسبة ومراجعة سلامة CI. لا تصبح حزم A–D منفذة لأن خطة تنفيذها سُجلت؛ يُغلق كل عمل منها لاحقاً بـStudy/Act واضح، بعد أمر مباشر من المالك.
